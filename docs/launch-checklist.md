# Launch checklist

Do these before the store goes live. Nothing here is done by default.

- [ ] Lift noindex: set `STORE_NOINDEX=false` in the production environment. One flag drives every page (`config/store.php`). A placeholder page also carries its own noindex: remove the `:noindex="true"` from `resources/views/pages/placeholder.blade.php` for a page once it has real content, or give the page its own view.
- [ ] Verify every homepage "Shop by standard" chip returns products on real data (the chips are in `config/homepage.php`; the tests only prove it against the fixture catalogue).
- [ ] Confirm the trust strip claims with the client (`config/homepage.php`, `trust`). The fourth slot is for a delivery claim that is not confirmed yet: leave it empty until it is.
- [ ] Confirm `pcntl` and `posix` are present in the server's PHP CLI before starting Horizon (`composer.json` fakes them under `config.platform` for Windows, so Composer will not warn).
- [ ] Replace every TBC in the store identity: name, legal name, company number, registered office, VAT number, phone and email (`STORE_*` in `.env`).
- [ ] Deploy sequence. This repository has no deploy script, so these are the steps for the server's own deploy routine, in order:
  1. `php artisan app:preflight`. It checks the PHP extensions (gd with WebP or imagick, exif, intl, bcmath, mbstring, zip, fileinfo, pcntl, posix, redis), the database, Redis, Meilisearch (host and key), that the products disk is writable and that `QUEUE_CONNECTION` is not `sync`. It also reports the CLI `memory_limit` and warns when the storage disk has less free space than `PREFLIGHT_MIN_FREE_DISK_GB` (default 10). It exits non-zero with one message per failure: do not carry on until it passes.
  2. `php artisan migrate --force`.
  3. First deploy only: `php artisan db:seed --class=CatalogueFoundationSeeder --force`. Do not run it on later deploys: it recreates reference records and categories that were deleted in the admin.
  4. `php artisan storage:link --force` (`--force` replaces a link left by an earlier release, so it is safe on every deploy).
  5. `php artisan catalogue:sync-redirects` (add `--dry-run` first to see what it would record). The first run on an existing database only takes a snapshot of every category path and records no redirects. The same command is also scheduled hourly (`withoutOverlapping`, in `routes/console.php`, not tied to `VENDORSYNC_SCHEDULE_ENABLED`), so the server's cron must run `php artisan schedule:run` every minute.
  6. Clear the cache, as the category menu is cached with its URLs. The cache uses its own Redis database (`REDIS_CACHE_DB=11`), so this cannot touch other sites on the same Redis.
  7. Restart the workers with `php artisan horizon:terminate` (the process manager starts Horizon again).
- [ ] After deploying a pricing-rule or markup change, run `php artisan vendorsync:catalogue SJ --dry-run` and `FS --dry-run` first. The first real run reprices every product once; review the held price changes (`sync_runs.report_path`) and accept the right ones with `--accept-price-changes=SKU,..` or `--accept-product=ID`. Ask Safety Jogger for GBP prices for products drafted `non_gbp_price`.
- [ ] `public/robots.txt` disallows `/lunar`, `/horizon`, `/cart`, `/checkout` and `/account`. It does not replace noindex: `STORE_NOINDEX` works through the meta tag only, and lifting it does not need a robots.txt change.
- [ ] Queues. Production runs three Horizon supervisors (`config/horizon.php`): `default` (3 processes, timeout 60), `images` (2, timeout 960, for the vendor image jobs, whose own timeout is 900; each job stops starting downloads 60 s before that, and the number of image workers is the number of concurrent requests per vendor host) and `conversions` (4, timeout 300). `REDIS_QUEUE_RETRY_AFTER` (1200) must stay above every job and supervisor timeout: a test fails when it does not. Locally, `composer dev` runs the worker for all three queues; with a bare `php artisan queue:work`, pass `--queue=default,images,conversions` or image jobs will not run.
- [ ] Conversions stay inline in the image job for now (`QUEUE_CONVERSIONS_BY_DEFAULT=false` in `.env.production.example`). The `conversions` queue and its supervisor are already configured, so queueing them later is an env change: set `QUEUE_CONVERSIONS_BY_DEFAULT=true` (`MEDIA_QUEUE` already defaults to `conversions`) and restart Horizon. Be aware that a failed conversion then lands in `failed_jobs` on the `conversions` queue instead of in the image run's report, so run `catalogue:verify-media` after every import.
- [ ] Queued search indexing is off for now: `SCOUT_QUEUE=false` in `.env.production.example`, so index updates are sent synchronously by the process that changes the product. Enable it later (`SCOUT_QUEUE=true`, then restart Horizon so the `default` workers pick it up) after the first import, as a separate decision, not as part of go-live. Do not enable it on a catalogue that has not been verified: with queued indexing a failed index job lands in `failed_jobs` instead of the import's report.
- [ ] After any import (catalogue or images), run `php artisan catalogue:verify-media`. It is read-only: it lists published products with no original image or with a missing generated conversion (`thumb`, `medium`, `large`), with counts and the first 20 product IDs, and exits non-zero when anything is missing. Add `--check-files` to also check the original and conversion files on disk. Image jobs run on the `images` queue, so wait for it to drain first. It does not detect a partial image set (a product with 5 of 6 images passes): those are listed by `php artisan vendorsync:status` and the image run's messages (`PARTIAL` and `HERO IMAGE FAILED`).
- [ ] After every import (catalogue, stock or images), run `php artisan catalogue:verify-index`, next to `catalogue:verify-media`. It is read-only and exits non-zero when anything is wrong. It compares the `products` index with the database: the expected set is every product Scout indexes (`Product::makeAllSearchableQuery()` and each product's `shouldBeSearchable()`; drafts and soft-deleted products are indexed too, so it is not "published"). It reports the expected count against the index's document count, up to 20 product IDs missing from the index and up to 20 documents that should not be there, the failed Meilisearch tasks for the index (count and the first few error messages), and compares the status and ex VAT price of 20 random indexed products with the database. A failed task stays in Meilisearch, so one old failure keeps the command failing: after you have dealt with it, pass `--since=<date>` to look only at newer tasks. Meilisearch processes documents asynchronously: if the command warns that tasks are still enqueued or processing, wait and run it again before acting on a difference. A missing product is fixed by reindexing it (`php artisan lunar:search:index`); an import run that fails with `Search indexing failed` has already cleared the hashes of the products concerned, so running that vendor again reindexes them (docs/vendorsync.md). When queued indexing is enabled later, also wait for the `default` queue to drain first.
- [ ] Before the first real image run, on the server with the production cache (Redis): check that the per-host slot lock fails an image cleanly. Image downloads reserve request slots under a Redis cache lock (`ImageDownloader::lockKey()`); the tests use the array cache, and there is no Redis on the Windows development machines. Choose an imported product (its vendor product ID is printed in the catalogue run's report) and its image host (`ws.safetyjogger.com` for Safety Jogger). Make sure Horizon is running, then:
  1. In `php artisan tinker`, hold the lock: `$lock = Cache::lock(app(App\Domain\VendorSync\Images\ImageDownloader::class)->lockKey('ws.safetyjogger.com'), 120); $lock->get();`
  2. In another shell: `php artisan vendorsync:images SJ --product=<vendor product ID>`. Each image should fail after about 5 s without any request to the vendor. `php artisan vendorsync:status` should then show the images run `failed`, a message containing `could not reserve a request slot on ws.safetyjogger.com within 5s (host throttle lock busy)`, and a `lock timeouts` count equal to the number of images. The job lands in `failed_jobs`: remove that one row with `php artisan queue:forget <id>`.
  3. Release the lock (`$lock->release();`) and run the same command again. The images should now download, `vendorsync:status` should show no lock timeouts, and `php artisan catalogue:verify-media` should pass.
