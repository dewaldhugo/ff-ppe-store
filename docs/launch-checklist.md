# Launch checklist

Do these before the store goes live. Nothing here is done by default.

- [ ] Lift noindex: set `STORE_NOINDEX=false` in the production environment. One flag drives every page (`config/store.php`). A placeholder page also carries its own noindex: remove the `:noindex="true"` from `resources/views/pages/placeholder.blade.php` for a page once it has real content, or give the page its own view.
- [ ] Verify every homepage "Shop by standard" chip returns products on real data (the chips are in `config/homepage.php`; the tests only prove it against the fixture catalogue).
- [ ] Confirm the trust strip claims with the client (`config/homepage.php`, `trust`). The fourth slot is for a delivery claim that is not confirmed yet: leave it empty until it is.
- [ ] Confirm `pcntl` and `posix` are present in the server's PHP CLI before starting Horizon (`composer.json` fakes them under `config.platform` for Windows, so Composer will not warn).
- [ ] The footer shows only the copyright line: the UK trading disclosure (company name, number, registered office, VAT number; `Store::disclosure()`) was taken out on request. Put it back, or confirm the client does not need it, before go-live.
- [ ] Replace every TBC in the store identity: name, legal name, company number, registered office and VAT number (`STORE_*` in `.env`). The address, phone and email are fixed in `config/store.php`.
- [ ] **Customer accounts: deploy prerequisite for `shared/.env`.** Production has no working mailer yet, and `STORE_REQUIRE_EMAIL_VERIFICATION` defaults to `true`. Before the first deploy of the customer accounts release, in the server's `shared/.env` do one of these, otherwise `php artisan app:preflight` fails by design (`mail: STORE_REQUIRE_EMAIL_VERIFICATION is on but MAIL_MAILER is log`) and the deploy must stop:
  - set `STORE_REQUIRE_EMAIL_VERIFICATION=false` (customers can register and use My Account without verifying; no verification email is sent), or
  - configure a real mailer: `MAIL_MAILER` (not `log` or `array`), the `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD` that mailer needs, and a real `MAIL_FROM_ADDRESS` (not empty or `@example.com`, which only warns). Then `php artisan config:cache` and `php artisan horizon:terminate`: the account emails run on the `default` queue.

  Also: password reset emails need a real mailer whatever the switch says. With `MAIL_MAILER=log` the reset link is only written to the log, so nobody can reset a password; `app:preflight` warns about it (without failing). The release adds one migration (`users.phone`, nullable), which the normal `migrate --force` step runs. Turning verification on later is safe: customers who registered while it was off are asked to verify on their next visit to My Account. See [docs/accounts.md](accounts.md).
- [ ] **Customer approval needs a working mailer.** New registrations cannot sign in until staff switch "Login active" on in the admin panel (Customers, Edit), and the registration and activation emails are the only way a customer hears about it. With `MAIL_MAILER=log` those emails are only written to the log, so a customer would wait with no word. Configure a real mailer (and run Horizon, the emails are on the `default` queue) before opening registration, whatever `STORE_REQUIRE_EMAIL_VERIFICATION` says. The release adds one migration (`users.approved_at`, `users.account_terms`); it sets `approved_at` for every existing user so nobody is locked out. Tell staff that "30 day account terms" is off for every customer until they switch it on, and that card payment is not built yet, so a customer without 30 day terms cannot place an order. See [docs/accounts.md](accounts.md).
- [ ] **Stripe card payments.** Set `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY` (live keys, `sk_live_` and `pk_live_`) and `STRIPE_WEBHOOK_SECRET` in `shared/.env`, then `php artisan config:cache`. Card payment stays "Not available at the moment" until both of the first two are set. In the Stripe dashboard (Developers, Webhooks) add the endpoint `https://<the live domain>/stripe/webhook` for the events `payment_intent.succeeded` and `payment_intent.payment_failed` and copy its signing secret into `STRIPE_WEBHOOK_SECRET`; Horizon must be running, because the webhook is processed on the `default` queue. The migration adds `stripe_payment_intents`. Before go-live pay once in test mode end to end (cards in docs/cart.md, Card payments), including the 3D Secure card and a declined card, and confirm the order appears in the admin as Payment Received; then once with a live card for a small amount and refund it from the Stripe dashboard. Check the Stripe account's business details, statement descriptor and the payment methods enabled (only cards are offered by the checkout).
- [ ] Deploy sequence. This repository has no deploy script, so these are the steps for the server's own deploy routine, in order:
  1. `php artisan app:preflight`. It checks the PHP extensions (gd with WebP or imagick, exif, intl, bcmath, mbstring, zip, fileinfo, pcntl, posix, redis), the database, Redis, Meilisearch (host and key), that the products disk is writable, that `QUEUE_CONNECTION` is not `sync` and that mail is configured (it fails when `STORE_REQUIRE_EMAIL_VERIFICATION` is on and `MAIL_MAILER` is `log` or `array`, and warns when verification is off and the mailer is `log` or `array`, or the from address is empty or `@example.com`). It also reports the CLI `memory_limit` and warns when the storage disk has less free space than `PREFLIGHT_MIN_FREE_DISK_GB` (default 10). It exits non-zero with one message per failure: do not carry on until it passes.
  2. `php artisan migrate --force`.
  3. First deploy only: `php artisan db:seed --class=CatalogueFoundationSeeder --force`. Do not run it on later deploys: it recreates reference records and categories that were deleted in the admin.
  4. `php artisan catalogue:restructure-categories` (add `--dry-run` first to see what it would change). One-off, for the deploy that introduces the full category tree (`App\Domain\Catalogue\Collections\CategoryTree`): it moves the contract categories the seeder created earlier into their contract parent and menu position, and renames a collection that still carries a superseded contract name (`CategoryTree::RENAMED_FROM`). Safe to run on every deploy after that: once the tree matches the contract it reports 0 changes. Run it before `catalogue:sync-redirects` below, since each move it makes is recorded as a 301 by the same observer that command's redirects come from. It also retires the categories the contract dropped (`CategoryTree::RETIRED`: Slippers, Plimsolls, Sandals & Summer Shoes): it deletes those collections, drafts every product left in no category and reindexes the products it touched, so run it before the vendor imports below and let it finish; the dry run reports the counts. After it runs, import each vendor once with `--force` (`vendorsync:catalogue SJ --force` and `FS --force`) so existing products move into their new leaf collections; an unchanged payload is otherwise skipped.
  5. `php artisan storage:link --force` (`--force` replaces a link left by an earlier release, so it is safe on every deploy).
  6. `php artisan catalogue:sync-redirects` (add `--dry-run` first to see what it would record). The first run on an existing database only takes a snapshot of every category path and records no redirects. The same command is also scheduled hourly (`withoutOverlapping`, in `routes/console.php`, not tied to `VENDORSYNC_SCHEDULE_ENABLED`), so the server's cron must run `php artisan schedule:run` every minute.
  7. Clear the cache, as the category menu is cached with its URLs. The cache uses its own Redis database (`REDIS_CACHE_DB=11`), so this cannot touch other sites on the same Redis.
  8. Restart the workers with `php artisan horizon:terminate` (the process manager starts Horizon again). Run it from the new release, after `current` points at it. It is always needed, not only for queue changes: running workers keep the old code in memory, and the image worker count (`HORIZON_IMAGES_PROCESSES`) and the other supervisor settings are only read when Horizon starts. If the deploy routine caches config (`php artisan config:cache`), run it for the new release before this step: with a config cache, `.env` is not read at runtime, so a changed `HORIZON_IMAGES_PROCESSES` does nothing until the cache is rebuilt.
  9. Image queue routing rules for this and every later deploy:
     - Image jobs go to the `images` queue only when the batch is dispatched by a release that contains the routing fix (`ImageRun` names the queue on the batch). Never start an image run (`vendorsync:images`, `vendorsync:catalogue`, or a scheduled one) from the old release: its jobs land on `default`, where the 3 default workers run them with the job's own 900 s timeout and block everything else on `default`. Do not run those commands from a shell that still sits in the old release directory, and if `VENDORSYNC_SCHEDULE_ENABLED=true`, do not let a scheduled run start between switching `current` and `horizon:terminate`.
     - Jobs already on `default` when the fix is deployed (the 181 seen in production) are not lost and need no action: the `default` supervisor keeps working that queue, they run with their own timeout and still count toward their batch, so the runs finish normally. Do not run `horizon:clear` or delete them: that leaves the batch and the images run `running` until its lock goes stale.
     - Check that the supervisors are what the repository says. `APP_ENV` must be `production`, the name of the only environment in `horizon.environments` that has supervisors, and its entries must stay empty (`[]`): a value set there silently overrides `defaults` and `HORIZON_IMAGES_PROCESSES` (a test enforces the empty entries in the repository, not on the server). On the server run `php artisan config:show horizon.environments`, `php artisan config:show horizon.defaults.supervisor-images` and `php artisan horizon:supervisors`: the images supervisor must list queue `images`, timeout 960, memory 192, maxJobs 100, and as many processes as `HORIZON_IMAGES_PROCESSES`.
     - Check the routing once after deploying: `php artisan vendorsync:images FS --product=<vendor product ID>`, then `php artisan tinker --execute="echo Queue::size('images').' '.Queue::size('default');"` (run it before the job finishes, or look at Horizon Recent Jobs). The job must be on `images`, not on `default`.
- [ ] After deploying a pricing-rule or markup change, run `php artisan vendorsync:catalogue SJ --dry-run` and `FS --dry-run` first. The first real run reprices every product once; review the held price changes (`sync_runs.report_path`) and accept the right ones with `--accept-price-changes=SKU,..` or `--accept-product=ID`. Ask Safety Jogger for GBP prices for products drafted `non_gbp_price`, and send them the `currency_diagnostics` of the run report for products that stay non-GBP after the re-fetches. Review `held_currency` in the same report: a variant held for many days (see `stored_price_written_at`) has a stale price.
- [ ] Set `VENDORSYNC_IMAGE_MAX_MEGAPIXELS=7` in the server `.env` (it overrides the config default), then `php artisan config:cache` and `php artisan horizon:terminate`. Verify once: `php artisan vendorsync:images SJ --product=<an id with a 2560 px image>` only dispatches the job; the Horizon worker decodes the image, so watch it with `ps -eo pid,rss,cmd | grep horizon` while the job runs (RSS in KB; expect about 110 MB, up to 150 MB for a very large file).
- [ ] Do not enable `VENDORSYNC_SCHEDULE_ENABLED` until the Footsure refresh policy is decided: a full weekly refresh of about 24,600 images is not viable (conditional requests are the likely approach). Not implemented.
- [ ] `public/robots.txt` disallows `/admin`, `/horizon`, `/cart`, `/checkout` and `/account`. It does not replace noindex: `STORE_NOINDEX` works through the meta tag only, and lifting it does not need a robots.txt change.
- [ ] Queues. Production runs three Horizon supervisors (`config/horizon.php`): `default` (3 processes, timeout 60), `images` (`HORIZON_IMAGES_PROCESSES` processes, default 2, timeout 960, memory 192, maxJobs 100, for the vendor image jobs, whose own timeout is 900; each job stops starting downloads 60 s before that, and the number of image workers is the number of concurrent requests per vendor host; sizing and the first import estimate are in docs/vendorsync.md) and `conversions` (4, timeout 300). The long-wait alert for `images` is 3 h (10800 s), because a first import queues thousands of jobs. Queue names are defined once, in `App\Support\Queues`. `REDIS_QUEUE_RETRY_AFTER` (1200) must stay above every job and supervisor timeout: a test fails when it does not. Locally, `composer dev` runs the worker for all three queues; with a bare `php artisan queue:work`, pass `--queue=default,images,conversions` or image jobs will not run.
- [ ] Conversions stay inline in the image job for now (`QUEUE_CONVERSIONS_BY_DEFAULT=false` in `.env.production.example`). The `conversions` queue and its supervisor are already configured, so queueing them later is an env change: set `QUEUE_CONVERSIONS_BY_DEFAULT=true` (the queue name is fixed to `conversions` in `config/media-library.php`) and restart Horizon. Be aware that a failed conversion then lands in `failed_jobs` on the `conversions` queue instead of in the image run's report, so run `catalogue:verify-media` after every import.
- [ ] Delete `MEDIA_QUEUE` from the production `.env` if it is there (it came from an earlier `.env.production.example`). Nothing reads it any more: the conversions queue name is fixed to `conversions` in `config/media-library.php`, so the variable is dead. If it was set to anything else, conversions were being queued on a queue no supervisor works.
- [ ] Queued search indexing is off for now: `SCOUT_QUEUE=false` in `.env.production.example`, so index updates are sent synchronously by the process that changes the product. Enable it later (`SCOUT_QUEUE=true`, then restart Horizon so the `default` workers pick it up) after the first import, as a separate decision, not as part of go-live. Do not enable it on a catalogue that has not been verified: with queued indexing a failed index job lands in `failed_jobs` instead of the import's report.
- [ ] After any import (catalogue or images), run `php artisan catalogue:verify-media`. It is read-only: it lists published products with no original image or with a missing generated conversion (`thumb`, `medium`, `large`), with counts and the first 20 product IDs, and exits non-zero when anything is missing. Add `--check-files` to also check the original and conversion files on disk. Image jobs run on the `images` queue, so wait for it to drain first. It does not detect a partial image set (a product with 5 of 6 images passes): those are listed by `php artisan vendorsync:status` and the image run's messages (`PARTIAL` and `HERO IMAGE FAILED`).
- [ ] After every import (catalogue, stock or images), run `php artisan catalogue:verify-index`, next to `catalogue:verify-media`. It is read-only and exits non-zero when anything is wrong. It compares the `products` index with the database: the expected set is every product Scout indexes (`Product::makeAllSearchableQuery()` and each product's `shouldBeSearchable()`; drafts and soft-deleted products are indexed too, so it is not "published"). It reports the expected count against the index's document count, up to 20 product IDs missing from the index and up to 20 documents that should not be there, the failed Meilisearch tasks for the index (count and the first few error messages), and compares the status and ex VAT price of 20 random indexed products with the database. A failed task stays in Meilisearch, so one old failure keeps the command failing: after you have dealt with it, pass `--since=<date>` to look only at newer tasks. Meilisearch processes documents asynchronously: if the command warns that tasks are still enqueued or processing, wait and run it again before acting on a difference. A missing product is fixed by reindexing it (`php artisan lunar:search:index`); an import run that fails with `Search indexing failed` has already cleared the hashes of the products concerned, so running that vendor again reindexes them (docs/vendorsync.md). When queued indexing is enabled later, also wait for the `default` queue to drain first.
- [ ] Before the first real image run, on the server with the production cache (Redis): check that the per-host slot lock fails an image cleanly. Image downloads reserve request slots under a Redis cache lock (`ImageDownloader::lockKey()`); the tests use the array cache, and there is no Redis on the Windows development machines. Choose an imported product (its vendor product ID is printed in the catalogue run's report) and its image host (`ws.safetyjogger.com` for Safety Jogger). Make sure Horizon is running, then:
  1. In `php artisan tinker`, hold the lock: `$lock = Cache::lock(app(App\Domain\VendorSync\Images\ImageDownloader::class)->lockKey('ws.safetyjogger.com'), 120); $lock->get();`
  2. In another shell: `php artisan vendorsync:images SJ --product=<vendor product ID>`. Each image should fail after about 5 s without any request to the vendor. `php artisan vendorsync:status` should then show the images run `failed`, a message containing `could not reserve a request slot on ws.safetyjogger.com within 5s (host throttle lock busy)`, and a `lock timeouts` count equal to the number of images. The job lands in `failed_jobs`: remove that one row with `php artisan queue:forget <id>`.
  3. Release the lock (`$lock->release();`) and run the same command again. The images should now download, `vendorsync:status` should show no lock timeouts, and `php artisan catalogue:verify-media` should pass.
